05 / 05
Proposed product foundation

What every project shares

  • A native project contract with stable identities, compositions, and asset references.
  • A render contract with a known runtime, dependencies, and output settings.
  • A review model linking original video context to current comment state and completed results.
  • Reproducible checkpoints that retain the source and asset versions needed to recreate the result.
Creator and team choices

What stays flexible

  • File locations: different drives, repositories, machines, or shared storage.
  • Organization: project and group names, memberships, and deliverables.
  • Hosting: local rendering, a shared machine, or a hosted service.
  • Collaboration: a solo creator, a shared project, or scoped links for reviewers.
Implementation decisions still to makeThe exact manifest schema, composition language, renderer interface, asset storage, and agent event integration. The initial collaboration model uses one project host and one editing job at a time. The example file names in this document illustrate responsibilities; they are not a finalized format or a claim that all of this is implemented.
Optional one-way migration from an existing editing project
Existing project→Agent-assisted conversion→Native Retake project

A separate migration tool could recreate an existing edit in the native format, then compare picture, timing, sound, and effects against the original. “1:1” would require verification. Once converted, ongoing editing and rendering use the native project system; the previous editor is not a runtime dependency.
